# AI 방식 작은 MAC 계산기

## 목적과 실행

이 프로젝트는 필터와 입력 패턴의 같은 위치 값을 곱해 누적하는 MAC을 작은 Python 프로그램으로 흉내 냅니다. 원본 `data.json`이 제공되지 않아 요청에 따라 학습용 합성 데이터를 만들었고, 실제 데이터가 오면 `data.json`만 교체하면 됩니다.

```powershell
python main.py
python -m unittest discover -s . -p "test_*.py"
```

메뉴 1은 3×3 직접 입력(중간 누적합 디버그 출력 선택 가능), 메뉴 2는 JSON 자동 분석, 메뉴 3은 홀수 크기 Cross/X 자동 생성입니다.

## 모드 1: 직접 입력

각 행에 숫자 3개를 입력하고, 행 개수·열 개수·문자·NaN·무한대를 검사합니다. 오류가 나면 `입력 오류: {이유} 다시 입력하세요.` 형식으로 안내한 뒤 행렬 전체를 다시 입력합니다. 결과 구역에는 입력 크기(3×3), A/B 점수, 10회 평균 MAC 시간(ms), 최종 판정을 출력합니다. `mac_2d(..., debug=True)`를 사용하면 각 곱셈 뒤의 중간 누적합을 볼 수 있습니다. 디버그 출력은 점수 계산에만 적용하고 시간 측정에서는 제외합니다.

모드 1의 동점 표시는 요구사항에 맞춰 `판정 불가`입니다. `EPSILON=1e-9`를 절대·상대 허용 오차로 함께 사용합니다. 작은 점수에서는 절대 오차가, 큰 점수에서는 상대 오차가 비교에 반영됩니다. 경계 예로 `1.0`과 `1.0+1e-10`은 동점이고, `1.0`과 `1.0+1e-6`은 다른 점수입니다. 약 1,000,000 규모에서는 상대 허용 오차가 약 0.001이므로 도메인에서 더 작은 차이도 구분해야 한다면 EPSILON을 낮추고, 큰 점수에서 반올림 오차가 커지면 실제 데이터 스케일과 허용 오차를 기준으로 조정합니다. 고정된 값이 모든 데이터에 맞는 것은 아닙니다.

## 모드 2: JSON 자동 분석

패턴 키는 `size_<양의정수>_<식별자>` 형식입니다. 식별자는 영문자·숫자·하이픈으로 구성합니다. 예: `size_3_1`, `size_25_case-a`. 크기 키는 `size_<양의정수>` 형식입니다. 키의 크기를 읽어 `filters[size_N]`를 선택하고, `+`/`cross`/`Cross`는 Cross, `x`/`X`는 X로 정규화합니다. 키 형식이 잘못되었거나 해당 크기의 필터가 없으면 사용 가능한 크기를 오류에 함께 표시합니다. `normalize_label`은 입력 표준화와 판정을 분리합니다. 지원하지 않는 라벨은 조용히 버리지 않고 경고와 함께 점수 계산에서 제외합니다.

점수가 높을수록 필터와 패턴의 같은 위치가 많이 일치하므로 유사도가 높다고 해석합니다. 최고 점수가 EPSILON 안에서 동점이면 모드 2는 `UNDECIDED`로 표시하고 정답과 다르므로 FAIL로 집계합니다. 이때 모든 동점 라벨과 같은 점수를 함께 출력합니다. 실패 요약은 키·필터 누락, 데이터 형식, 예측·기대값 불일치로 나눕니다.

모드 2는 다음 성능 표도 출력합니다.

```text
크기 | 평균 시간(ms) | 반복수 | 위치 연산 수(N²)
3 | 실행 시 측정 | 10 | 9
5 | 실행 시 측정 | 10 | 25
13 | 실행 시 측정 | 10 | 169
25 | 실행 시 측정 | 10 | 625
```

시간 측정은 `time.perf_counter()`로 MAC 호출을 반복합니다. 호출 안의 행렬 검증(`validate_matrix`), 반복문, 곱셈·누적은 포함하고, 사용자 입력, JSON 읽기, 패턴 생성, 결과 출력은 제외합니다. 시간복잡도는 N×N 위치를 방문하므로 O(N²)입니다. 크기가 3에서 5로 증가하면 연산 수가 9에서 25로 증가하는 것처럼 크기의 제곱에 비례합니다. 다른 크기 점수를 한 표에서 비교해야 한다면 데이터 범위를 먼저 정한 뒤 최대 가능 점수 대비 비율(예: 0–1 또는 %)을 계산하는 정규화 옵션을 추가할 수 있습니다. 현재는 같은 크기의 필터끼리 원점수를 비교합니다.

정규화율은 `원점수 / 최대 가능 점수 × 100%`로 계산할 수 있습니다. 최대 가능 점수는 필터·패턴 값의 범위에 따라 달라지므로 기준을 먼저 정해야 합니다.

## 결과 리포트

기록된 실제 실행 결과(2026-11-08)는 `evidence/test-run.txt`에 보관되어 있습니다. 아래 시간은 당시 컴퓨터에서 얻은 예시이며 현재 성능 보장은 아닙니다.

1. 기록된 자동 테스트 6개가 모두 통과했습니다.
2. Cross 필터와 X 입력의 MAC 점수는 1.0이었습니다.
3. X 필터와 같은 입력의 MAC 점수는 5.0이었습니다.
4. 해당 직접 입력 예시의 최종 판정은 B였습니다.
5. A와 B 점수가 모두 5.0인 예시의 판정은 `판정 불가`였습니다.
6. `size_3_1`은 Cross=1.0, X=5.0, 기대=X로 PASS였습니다.
7. `size_5_1`은 Cross=9.0, X=1.0, 기대=Cross로 PASS였습니다.
8. JSON 분석 결과는 전체 2건, PASS 2건, FAIL 0건이었습니다.
9. 3×3 성능 기록은 평균 0.007940 ms, 위치 연산 9회였습니다.
10. 5×5 성능 기록은 평균 0.016950 ms, 위치 연산 25회였습니다.
11. 13×13 성능 기록은 평균 0.090750 ms, 위치 연산 169회였습니다.
12. 25×25 성능 기록은 평균 0.344320 ms, 위치 연산 625회였습니다.

새 실패 출력의 형식 예시(표시 형식 설명이며 새 실행 로그는 아닙니다): `size_7_1`에 `size_7` 필터가 없으면 `FAIL [key]`와 사용 가능한 `size_3, size_5, size_13, size_25`가 표시됩니다. 지원하지 않는 라벨은 경고로 표시되고, Cross/X 점수가 같으면 `동점 후보(동일 점수): Cross=..., X=...`와 함께 FAIL 요약의 예측·기대값 불일치에 포함됩니다.

실패 원인 분석 기준은 다음과 같습니다.

1. 행렬 크기가 다르면 MAC을 시작하지 않습니다.
2. 문자가 들어오면 숫자 변환 단계에서 실패합니다.
3. NaN과 무한대는 결과 오염을 막기 위해 거부합니다.
4. 패턴 키가 `size_<양의정수>_<식별자>` 형식이 아니면 해당 사례만 FAIL입니다.
5. 해당 크기의 필터가 없으면 해당 사례만 FAIL입니다.
6. 지원하지 않는 라벨은 경고와 함께 필터 점수에서 제외됩니다.
7. 지원 필터가 하나도 없으면 FAIL 이유를 남깁니다.
8. 최고 점수가 동점이면 모드 2에서 UNDECIDED와 모든 동점 후보·점수를 표시합니다.
9. 예상 라벨과 예측 라벨이 다르면 FAIL입니다.
10. JSON 파일 자체가 없거나 문법이 틀리면 분석을 시작할 수 없습니다.
11. 1000×1000은 1,000,000개 위치라 Python 반복 비용이 커집니다.
12. 실행 시간은 CPU·Python 버전·다른 프로세스에 따라 달라집니다.

## 큰 입력·CPU/NPU 분석

1000×1000은 O(N²)이며 모든 값을 메모리에 둔 뒤 직렬 Python 반복으로 처리하면 CPU 계산과 메모리 접근이 병목입니다. 크기 N₀에서 측정한 시간이 T₀라면 같은 구현의 대략적인 예상은 `T(N) ≈ T₀ × (N/N₀)²`입니다. 예를 들어 25×25에서 0.344 ms가 걸렸다면 1000×1000의 단순 추정은 약 551 ms입니다. 이 값은 Python 반복의 고정 비용과 캐시 효과를 무시한 거친 추정이며 실제 시간은 반드시 측정해야 합니다.

프로파일링은 `python -m cProfile -s cumulative main.py`로 함수별 누적 시간을 확인합니다. 메모리와 연산 시간을 함께 측정하려면 패턴 생성 전 `tracemalloc.start()`를 시작하고, `time.perf_counter()` 전후를 MAC 호출에 두어 입력 크기, 점수, 경과 ms, peak bytes를 기록합니다. 생성 시간과 MAC 시간은 별도 구간으로 측정해야 원인을 구분할 수 있습니다. 비교 지표는 N, 실행 ms, peak 메모리(bytes), 반복 횟수, Python 버전입니다.

최적화 우선순위는 ① 행 단위 생성으로 메모리 피크를 줄이고, ② 실제 측정으로 병목을 확인하고, ③ NumPy 벡터화나 C 확장으로 반복 비용을 줄이고, ④ 필요할 때 병렬 처리를 검토하는 순서입니다. 행 단위 처리가 항상 더 빠르다고 가정하지 않습니다.

CPU는 소수의 코어가 범용 명령을 순차 처리하므로 Python 루프 오버헤드가 큽니다. NPU는 많은 MAC을 병렬 처리할 수 있지만 데이터 이동, 버퍼 배치, 메모리 대역폭이 병목이 될 수 있습니다. NPU를 적용한다면 입력을 연속된 배열과 고정 dtype으로 준비하고, 여러 행렬을 배치로 묶어 전송하며, 같은 필터를 장치 메모리에 재사용해 CPU↔NPU 왕복을 줄입니다. 전처리·전송·커널 시간을 따로 측정해 계산이 빨라진 만큼 전송 비용이 늘지 않았는지 확인합니다. 이 프로젝트에서는 실제 NPU를 실행하지 않았으므로 이 부분은 이론 비교입니다.

## 확장 절차

새 라벨을 추가할 때는 `normalize_label` 매핑 추가→`analyze_json` 점수·동점 출력 확인→`test_main.py`에 단위 테스트 추가→`data.json` 예시 추가→README 지원 라벨과 결과 표 갱신 순서로 진행합니다. 수정 파일 체크리스트는 `main.py`(정규화·분석), `test_main.py`(새 라벨 테스트), `data.json`(입력 예시), `README.md`(지원 라벨·결과)입니다. 저장 포맷이나 필드가 바뀌면 `load_data`, JSON 검증, 테스트, 예시 데이터를 함께 수정합니다.

단위 테스트 템플릿:

    def test_new_label_alias(self):
        self.assertEqual(normalize_label("새별칭"), "Cross")

예를 들어 새 별칭을 `cross` 라벨로 추가했다면, 위 기대값을 확인하는 테스트와 해당 별칭이 든 JSON 사례를 함께 추가합니다.
